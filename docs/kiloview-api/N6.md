## 1. Authentication

### Obtain an API token

`POST /api/user/authorize.json`

```json
{
  "user": "admin",
  "password": "YOUR_DEVICE_PASSWORD"
}
```

Read `data.token` and `data.alias`. Construct cookies using the returned token and alias. The project sends `username`, `user`, `alias` and `token`. It uses `Admin` if alias is absent. This is not Bearer authentication.

```http
Cookie: username=admin; user=admin; alias=Admin; token=TOKEN_FROM_LOGIN
```

### PowerShell login and read-only checks

First load `Invoke-KvJson` from [Shared conventions](COMMON.md#powershell-json-validation-helper). Replace the illustrative address. Use the actual device credentials; the example prompts for them.

```powershell
$deviceBase = 'http://192.0.2.60'
$deviceCredential = Get-Credential -UserName 'admin'
$deviceUri = [uri]$deviceBase
$session = New-Object Microsoft.PowerShell.Commands.WebRequestSession
$login = Invoke-KvJson -Uri "$deviceBase/api/user/authorize.json" -Method POST -Body @{
    user = $deviceCredential.UserName
    password = $deviceCredential.GetNetworkCredential().Password
}
if ([string]::IsNullOrWhiteSpace([string]$login.data.token)) { throw 'No API token returned' }
$alias = [string]$login.data.alias
if ([string]::IsNullOrWhiteSpace($alias)) { $alias = 'Admin' }
$cookies = @{
    username = $deviceCredential.UserName
    user = $deviceCredential.UserName
    alias = $alias
    token = [string]$login.data.token
}
foreach ($name in $cookies.Keys) {
    $cookie = New-Object System.Net.Cookie($name, $cookies[$name], '/')
    $session.Cookies.Add($deviceUri, $cookie)
}
$firmware = Invoke-KvJson -Uri "$deviceBase/api/firmware/get.json" -Session $session
$hostname = Invoke-KvJson -Uri "$deviceBase/api/device/get_hostname.json" -Session $session
$mode = Invoke-KvJson -Uri "$deviceBase/api/mode/get.json" -Session $session
$firmware.data
$hostname.data
$mode.data
```

Keep token values opaque. Session lifetime is not established by the project.

### First login and enabling API permission

Web login and API authorization are separate paths. Successful web login does not prove API permission is enabled.

| Method / path | Body / response used |
| --- | --- |
| `POST /api/users/login.json` | Body: `user`, `password`; response: `data.token`, `data.alias`, `data.changed` |
| `POST /api/users/modify.json` | Initial password edit: `id`, `username`, `password`, `passwordAgain` |
| `POST /api/users/modify.json` | API permission edit: `id`, `alias`, `web: true`, `api: true` |

`changed: false` is treated as first-login state. The project performs the password edit first, logs in again using the replacement credentials, and enables API permission in a separate edit. It then verifies `/api/user/authorize.json` with the replacement credentials.

Password-change example, for changing the password of an existing `admin` account:

```json
{
  "id": "admin",
  "username": "admin",
  "password": "YOUR_NEW_DEVICE_PASSWORD",
  "passwordAgain": "YOUR_NEW_DEVICE_PASSWORD"
}
```

API-permission edit after reauthentication:

```json
{
  "id": "admin",
  "alias": "Admin",
  "web": true,
  "api": true
}
```

Use the returned alias where available. These requests change credentials or permissions. Account renaming and a universal first-login license endpoint are not established by this guide. License-route candidates in the source are compatibility probes, not confirmed API contracts; see section 11.

## 2. Inventory and status reads

| Method / path | Fields consumed by the project | Notes |
| --- | --- | --- |
| `GET /api/firmware/get.json` | `data.softwareVersion`; optional `serialNumber` / `serial_number` | Software version is used for firmware matching |
| `GET /api/device/get_hostname.json` | `data.hostname` | Hostname is mutable |
| `GET /api/network/get.json` | `data[]`: `device`, `ip`, `mac`, `dynamic` | Adapter currently uses first entry |
| `GET /api/mode/get.json` | `data.mode` | `encoder` or `decoder` |
| `GET /api/mode/status.json` | `data.status` | `ready` is used during mode recovery |
| `GET /api/device/status.json?types=ndihx` | Root or `data`: `serial_number`, signal and resolution fields | Encoder-service probe; may fail in decoder mode |
| `GET /api/decoderMode/current/get.json` | Root or `data`: current decoder fields | Codec-service readiness/fallback probe; exact capital `M` |
| `GET /api/decoder/current/get.json` | `data`: `name`, `url`, `original_url`, `ip`, `online` and possible channel fields | Current selected source |
| `GET /api/decoder/output/get.json` | `data.resolution` | HDMI output status used by the project |

Signal lookup tries `signal`, `video_signal`, then `input_signal`. Resolution lookup tries `resolution`, `input_resolution`, then `video_resolution`. The current input probe treats empty, `0`, `none`, `no signal`, `unknown`, `offline` and `false` as absent, ignoring case and normalizing hyphens/underscores. These are parser rules, not a complete vendor enum.

For stable identity, prefer a hardware serial. The project falls back through firmware/status identity, the factory `N6-<serial>` hostname form, and MAC address when needed. Do not derive permanent identity from a renamed hostname or IP address.

**Vendor cross-check:** v3.0 lists `/api/encoder/ndi/status.json` for encoder status, whereas this integration probes `/api/device/status.json?types=ndihx`. Treat the former as a separately documented route, not a verified interchangeable alias. [N5/N6 API v3.0, §3.3](https://enstatic.kiloview.com/wp-content/uploads/2025/09/NEW-N5ampN6-APIEN-version-3.0-1.pdf#page=18)

## 3. Network and hostname

### Static IPv4

Read `/api/network/get.json` first and reuse the actual `device` value.

`POST /api/network/modify.json`

```json
{
  "device": "eth0",
  "dynamic": "n",
  "ip": "192.0.2.60",
  "mask": "255.255.255.0",
  "gw": "192.0.2.1",
  "dns": "192.0.2.1"
}
```

All fields above are strings. `dynamic: "n"` selects the static form used by this project. DHCP mutation is not implemented here. An address change may terminate the HTTP connection; reconnect and confirm the configuration and physical identity before marking it complete.

### Hostname

`POST /api/device/set_hostname.json`

```json
{"hostname": "STUDIO-KV-001"}
```

Read back `/api/device/get_hostname.json`. Hostname and NDI channel/group are separate settings.

## 4. Role switching and codec readiness

`POST /api/mode/switch.json`

```json
{"mode": "decoder"}
```

The other supported project value is `encoder`. Switching interrupts codec operation.

The project safeguards for firmware 2.00 are:

1. Establish the current role first. If already at the target, skip the switch.
2. Before a decoder-to-encoder switch, read `/api/preview/get`, remove existing preview positions using `/api/preview/source/remove`, and verify the preview list is empty. This deletes those preview entries; save/rebuild them if they must be retained.
3. Request the role change once.
4. Reauthenticate while polling `/api/mode/status.json`, `/api/mode/get.json`, and the target service: encoder device status or `/api/decoderMode/current/get.json`.
5. Require five consecutive checks reporting `ready`, the desired role and a responsive target codec service. The project allows up to 90 seconds after the write.

The web service can be available while the codec proxy returns `0201001`. That error is not evidence that the opposite role is active. When `mode/get` is temporarily unavailable, the code requires three consistent fallback codec probes before using that inferred role. Do not blindly alternate modes or repeatedly reboot the device.

## 5. Encoder identity and transport

### Configure the NDI group and channel

`POST /api/encoder/ndi/set_config.json`

```json
{
  "types": "ndihx",
  "device_group": "STUDIO",
  "channel_name": "CAM-01"
}
```

Read with `POST /api/encoder/ndi/get_config.json`, body `{"types":"ndihx"}`. Inspect the object at `data`. Repeat using `types: "ndifull"` when Full NDI is available. The project tolerates Full NDI failures in selected identity/transport operations because firmware/license capability can vary; confirm which sender is actually active.

Initial onboarding also uses the following project route for **each** profile:

`POST /api/device/modify.json`

```json
{
  "types": "ndihx",
  "device_group": "STUDIO",
  "channel_name": "CAM-01",
  "machine_name": "STUDIO-KV-001"
}
```

It separately writes the system hostname. Do not assume updating only `channel_name` changes the hostname. This onboarding route is not listed in the inspected v3.0 manual.

### Multicast sender

`POST /api/encoder/ndi/set_config.json`

```json
{
  "types": "ndihx",
  "ndi_connection": "multicast",
  "netprefix": "239.194.1.0",
  "netmask": "255.255.255.0",
  "ttl": 1
}
```

| Field | Project request type / purpose |
| --- | --- |
| `types` | String: `ndihx` or `ndifull` |
| `ndi_connection` | String: `multicast`; `unicast` for reversion |
| `netprefix` | String: multicast allocation prefix |
| `netmask` | String: mask paired with the prefix |
| `ttl` | Integer: requested time-to-live |

Write the complete transport tuple together. The code notes that this restarts the sender. Read back with `get_config.json` for the same profile and compare transport, prefix, mask and TTL. The current verifier tolerates a missing TTL field; absence does not independently confirm the requested TTL.

Revert using `{"types":"ndihx","ndi_connection":"unicast"}` and repeat for `ndifull` as applicable. Existing prefix/mask values may remain stored after switching transport.

**Hardware:** The 14 August 2026 N6 test on `2.00.0009.0134` confirmed both profiles' saved allocation and captured traffic inside `239.194.1.0/24`. This does not establish identical behavior on untested firmware. [Acceptance report](SOURCES.md#historical-hardware-evidence)

## 6. Discovery Server and manual sources

### Discovery Server

`POST /api/device/set_discovery_server.json`

```json
{
  "enable": true,
  "servers": [
    {"ip": "192.0.2.10", "group_name": "STUDIO"}
  ]
}
```

Read `GET /api/device/get_discovery_server.json`. Verify enabled state and a matching `servers[]` entry at the root or inside `data`. Reapply and verify after the final role is active.

**Vendor difference:** v3.0 describes a string `address` field, including comma-separated servers. The current project uses the grouped `servers[]` shape above. Check firmware support before substituting either form. [N5/N6 API, §§10.6-10.7](https://enstatic.kiloview.com/wp-content/uploads/2025/09/NEW-N5ampN6-APIEN-version-3.0-1.pdf#page=61)

### Manual discovery targets

`POST /api/decoder/discovery/set_manual_targets.json`

```json
{
  "ip": ["192.0.2.61", "192.0.2.62"],
  "group_name": ["STUDIO"]
}
```

`ip` is an array of sender/identity-source IP addresses, not multicast group addresses. Read discovered legacy sources with `GET /api/decoder/discovery/get.json`; source records are in `data[]`. Use returned names and `original_url` (falling back to `url`) for selection. Discovery Server configuration alone is not proof that a sender is discoverable.

## 7. Decoder sources, presets and output

Current firmware integration uses a source-group/layout API in addition to the older single-output API. Source IDs, group IDs, output IDs and position IDs belong to different namespaces; retain their returned values.

### Discover grouped sources

`POST /api/source/groups/list`

```json
{"is_need_stream": true, "show_template": false}
```

Iterate `data[]`, then each group's `streams[]`. Fields used include group `id` and stream `id`, `name`, `url`, `address`, `type`, `trans_mode`, `listener_port`. Copy the source's returned URL. The project prefers `listener_port`, or parses the URL's port when comparing stale advertisements; a larger port is only a project tie-breaker, not a universal timestamp.

### Add a preview/feed preset

`GET /api/preview/get` returns preview entries in `data.position[]` with `id`, `stream_id`, `stream_name`, `stream_url`.

`POST /api/preview/source/modify`

```json
{
  "from": {
    "type": "source",
    "stream_id": "STREAM_ID_FROM_DISCOVERY",
    "stream_name": "STUDIO-KV-002 (CAM-02)",
    "stream_url": "SOURCE_URL_FROM_DISCOVERY",
    "pos_id": ""
  },
  "to": {
    "type": "preview",
    "stream_id": "STREAM_ID_FROM_DISCOVERY",
    "stream_name": "STUDIO-KV-002 (CAM-02)",
    "stream_url": "SOURCE_URL_FROM_DISCOVERY"
  }
}
```

Omit `to.pos_id` to append. Supplying a guessed position caused `0304002` in project investigations. The adapter enforces a ten-feed preview capacity; this is its implementation limit, not a promise for all N6 firmware.

Remove a returned preview position using `POST /api/preview/source/remove`, e.g. `{"pos_id":3}`. Read back the list after edits. Populating a preview bank is separate from selecting the HDMI output.

### Select a source on a layout output

1. `GET /api/output/list`: choose the intended output from `data[]` and retain its string `id`.
2. `GET /api/output/get?output_id=<encoded-id>`: read `data.position[]` and retain the desired position's numeric `id`.
3. `POST /api/output/source/set` using the returned source/output/position values.

```json
{
  "from": {"type": "source", "output_id": "OUTPUT_ID_FROM_LIST"},
  "to": {
    "type": "output",
    "stream_id": "STREAM_ID_FROM_DISCOVERY",
    "stream_name": "STUDIO-KV-002 (CAM-02)",
    "stream_url": "SOURCE_URL_FROM_DISCOVERY",
    "output_id": "OUTPUT_ID_FROM_LIST",
    "pos_id": 1
  }
}
```

`pos_id: 1` is illustrative; use the actual position returned. Read the output again and verify `stream_id`/`stream_name`. The project identity-card routine selects the first output and first position; a general controller should choose the intended output explicitly.

### Legacy single-output selection

`POST /api/decoder/current/set.json`

```json
{
  "name": "STUDIO-KV-002 (CAM-02)",
  "url": "SOURCE_URL_FROM_DISCOVERY"
}
```

Read `/api/decoder/current/get.json` (or the decoderMode fallback) and compare name/URL. The project attempts this when the layout path is unavailable or does not complete selection.

## 8. Decoder multicast/unicast transport

There is no global N6 receiver toggle in this integration. There **is** a per-source transport edit:

`POST /api/source/groups/streams/modify`

Start with the complete stream object returned by `/api/source/groups/list`, preserve its fields, then add/replace:

| Field | Value |
| --- | --- |
| `group_id` | Parent group's returned ID as a string |
| `stream_id` | Source's returned ID as a string |
| `ndi_name` | Source's returned `name` |
| `trans_mode` | `multicast` or `unicast` |

This table is a patch to the returned record, **not** a complete standalone payload. Read the source groups again and match group ID plus stream ID to verify the retained `trans_mode`.

For multicast, the code registers sender IPs/groups, selects matching `type: "ndi"` source records by `address`, and changes their transport. When reverting, it edits discovered sources currently marked multicast to unicast. New sources may need this edit when they later appear. The older repository README's statement that N6 decoder transport cannot be selected is incomplete relative to the current adapter.

## 9. Blanking the decoder

`POST /api/decoder/preset/set_blank.json`

```json
{"color": "#000000"}
```

Read the current source. If not already blank, select preset zero:

`POST /api/decoder/current/set.json`

```json
{"id": "0"}
```

The project uses a **string** ID here. Firmware 2.00 can reject zero selection with `0301003` after the source has already disappeared. The project accepts that situation only when readback confirms: `online` is not boolean true, `name` and `url` are empty, and `ip` is empty or `0.0.0.0`.

For a standalone client, perform that readback after a successful selection too. The current N6 implementation reads before selection and in the error-recovery case; its successful selection path does not itself perform another immediate read.

Hardware evidence from September confirms the application's completion checks passed on N6 `2.10.0011.0885`; physical screen blanking was not independently observed. [September test](https://github.com/JohnDevAc/Kiloview-Job-Configurator/blob/9d431ce25f83e37e0f05f3301ade5b2ac8ac9cd9/E2E-ONBOARDING-TEST-2026-09-05.md)

## 10. KiloLink and firmware

### KiloLink configuration

The project tries multiple firmware-dependent paths in order. None should be treated as a universal N6 endpoint solely because it is in the fallback list.

| Evidence / method / path | Payload |
| --- | --- |
| Compatibility probe: `POST /api/KiloLink/set` | Configuration object below |
| Compatibility probe: `POST /api/kilolink/set` | Same object |
| Project legacy integration: `POST /kilolink/kilolink/Set.json` | Wrap object as `{"cfg": ...}` |
| Project readback: `GET /kilolink/kilolink/Get.json` | Inspect root `cfg` |
| Compatibility probe: `GET /api/platform/set.json?MASTER_ADDR=<ip>&MASTER_PORT=<port>&AUTH_CODE=<key>` | URL-encoded query values; changes configuration despite GET |

Configuration object:

```json
{
  "ip": "192.0.2.10",
  "port": 50000,
  "ifname": ["eth0"],
  "key": "YOUR_KILOLINK_ONBOARDING_CODE",
  "crypto": false,
  "enable": true
}
```

`port` is numeric; `ifname` is an array; `crypto` and `enable` are booleans. This configures the device-link service, not KiloLink's web-management port. The example follows the project's unencrypted device-link setting. Readback checks enabled state, address, port, key and interface. Route-level success of every fallback has not been established by the historical onboarding reports.

### Firmware

`POST /api/firmware/upgrade.json`, multipart binary field `upload` and text field `path`. See the exact [shared multipart contract](COMMON.md#4-firmware-upload-contract). The N6 parser's header ordering requirement is supported by a successful recovery upload, not merely an inferred request format.

## 11. Errors and unverified first-login routes

| Symptom | Project interpretation / response |
| --- | --- |
| Web login succeeds; API authorization fails | Check API permission separately |
| `0201001` | Codec proxy unavailable; determine readiness before further writes |
| `0304002` adding preview | Do not invent an append position ID |
| `0301003` selecting blank | Read current source; only accept a proved already-blank state |
| `0401003` uploading firmware | Inspect all error messages and multipart layout; that code alone does not prove one universal cause |
| No discovered source | Check active sender, matching group, Discovery Server, IP targets and stale listener advertisements |

The license helper probes `/api/users/accept_eula.json`, `/api/sys/accept_eula.json`, `/api/sys/eula/accept.json`, `/api/device/accept_eula.json`, `/api/device/set_eula.json`, `/api/license/accept.json`, plus paths discovered in web assets. It tries several request forms. This heuristic is not a documented universal license API and the helper's return value is not conclusive license-state verification. Use the device UI's actual first-login flow when a stable endpoint has not been established.
